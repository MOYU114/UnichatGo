# 异步执行与水平扩容路线图

| 项目 | 内容 |
| --- | --- |
| 更新日期 | 2026-10-12 |
| 当前阶段 | M1 已设计/独立审阅；M2 核心事务完成验证；M3-M6 实施中，未达完整发布门槛 |
| 实施状态 | 用户已授权实施；新增异步路径默认关闭；详细证据与未完成项见 implementation-checkpoint-2026-10-12.md |
| 目标 | 在保留聊天消息 MySQL 持久化和本机缓存的基础上，建立可恢复、跨实例幂等、同会话串行的后台执行链路 |
| 路线 | SQL-first + 轻量事务 Outbox + Redis Streams pull + 最小持久执行/结果凭证 |
| 排期 | 按依赖推进；负责人、工期、容量目标在详细设计与基线测量后确定，不在本文件猜测 |

## 1. 已确认的设计基线

依据 [ADR-002](../design-review/adr-002-lightweight-outbox-and-durable-evidence.md)、[ADR-003](../design-review/adr-003-async-execution-and-history.md) 及前三轮确认记录:

1. 受理时将用户消息、必要请求关联/凭证和 Outbox 在同一 MySQL 事务中提交，之后才确认受理。暂不预设完整 `chat_requests` 表，也不先做 MySQL 常态任务领取队列。
2. Redis Streams 承担共享投递，Worker 按可用容量阻塞 pull；内存保留为缓存和本机并发保护，不作为唯一任务或幂等事实源。
3. 最终结果及必要状态提交成功后再确认消费；浏览器收到响应或 SSE 不是提交及 ACK 的前提。
4. 同会话有界排队、按受理顺序执行；uncertain 阻塞该会话后续执行并暂拒新增。不同会话在配额范围内并行。
5. 最小幂等凭证随会话保留。同 key 同 payload 返回原请求；同 key 不同 payload 返回 409，完成后不删除去重凭证。
6. 后端可靠受理后独立完成任务。刷新、断网、关闭页面不取消任务；用户通过受鉴权的历史 API 从 MySQL 恢复结果。
7. 短暂内部故障由后台恢复；供应商失败、内部最终失败和结果不确定均如实展示。上游可能已执行时，不盲目自动再次调用。

本路线图不承诺上游模型 exactly-once 执行/计费，不承诺任意存储灾难下零丢失，也不把逐 token 重放、独立 SSE 微服务或“停止生成”UI 设为首版必做项。

## 2. 阶段总览与依赖

| 阶段 | 目标 | 前置依赖 | 当前状态 | 发布边界 |
| --- | --- | --- | --- | --- |
| M0 | 确认框架与业务语义 | 调研与讨论 | 已完成设计确认 | 不是代码完成或上线许可 |
| M1 | 详细契约、故障协议与测试设计 | M0 | 已设计并独立审阅 | 相关设计通过后才实施对应模块 |
| M2 | 最小持久事实与原子受理/提交 | M1 核心契约 | 核心实现/真实 MySQL 验证通过 | 仅内部测试，不单独开放新受理链路 |
| M3 | Outbox、Streams 与会话串行执行 | M2 | 主链路已验证；M3.5 功能等价未完成 | 完成投递到结果提交的闭环，仍限测试环境 |
| M4 | 前后台解耦、历史恢复与异常恢复 | M3 | 核心闭环已验证；完整故障/浏览器验收仍待补 | 单实例异步闭环通过验收；生产开放还需 M5-M6 |
| M5 | 全局容量、共享附件与运行底座 | M1 对应分支；集成依赖 M3-M4 | 已实现基础能力；功能等价、运行验收未完成 | 多实例必要能力齐备，等待综合验收 |
| M6 | 故障演练、容量验证与灰度上线 | M2-M5 全部通过 | 隔离进程测试通过；容量/灰度/回滚/灾难恢复未验收 | 达标后才开放多实例生产流量 |
| M7 | 按观测结果优化吞吐与成本 | M6 和真实指标 | 后续候选 | 不预先引入新 MQ 或自动扩缩平台 |

```text
M0 -> M1 -> M2 -> M3 -> M4 --------> M6 -> M7
       |                            ^
       +-> M5 对应分支设计/准备 -----+
                  与 M3/M4 集成验收
```

M5 的配额与附件工作在接口稳定后可以与核心链路开发并行，但不能因为排在表格后面，就推迟到多实例上线以后。阶段完成要求运行证据；以下勾选只覆盖该条明确范围。章节有未完成前置条件时，不视为整个阶段完成。

## 3. M0: 已完成的设计确认

- [x] 确认 SQL-first、轻量 Outbox 和 Redis Streams 阻塞拉取路线。
- [x] 确认允许最小 SQL 改造，不以完整请求表作为前提，内存降为缓存。
- [x] 确认会话排队、幂等保留、uncertain 处理及前后台独立生命周期。
- [x] 确认最终历史以 MySQL 为准，以及内部/上游错误的真实展示边界。

证据: [Round 1](../design-review/round-001.md)、[Round 2](../design-review/round-002.md)、[Round 3](../design-review/round-003.md)。这些完成项只代表用户已确认设计原则。

## 4. M1: 详细契约与故障协议

### 工作项

- [x] M1.1 比较“现有消息加字段”和“紧凑执行凭证表”，确定物理 schema、唯一索引、历史消息兼容与版本迁移。明确不把完整历史或每个 token 重复写入凭证。
- [x] M1.2 定义请求身份、payload 规范化/hash、冻结的 Provider/model/附件输入、凭证保留和资源删除语义。
- [x] M1.3 定义受理、开始外部调用、最终提交、会话推进的短事务边界及合法状态迁移；区分 outbox published、PEL pending、业务 completed。
- [x] M1.4 设计 session sequence、有效 owner/lease/fence、跨 SQL/Redis 的条件完成协议，以及非头任务、过期 Worker 和 uncertain 的处置流程。
- [x] M1.5 定义提交与历史 API、稳定错误码、旧接口兼容和前端 client ID 生命周期；在线 SSE 如保留，只作为独立观察渠道。
- [x] M1.6 编写故障注入矩阵、可控 mock Provider 和真实 MySQL/Redis 集成测试计划；核定版本及连接池/持久化配置项，参数待测。

**交付物:** 可审阅的字段/索引设计、状态迁移与时序、接口契约、迁移方案和测试用例清单。

**验收门槛:** 任意“已确认受理”“已开始调用”“结果已提交但未 ACK”的崩溃窗口，都有明确恢复依据；无用 Redis 锁或 PEL 单独替代 SQL 条件提交的空白；未决产品选择单独回到 design-review 审阅。

## 5. M2: 最小持久事实与事务服务

### 工作项

- [x] M2.1 引入可升级已有库的版本迁移；配置共享 MySQL 的连接池与超时；保留开发/单机模式兼容方案，不把 SQLite 当集群存储。
- [x] M2.2 实现鉴权后的幂等受理事务: 用户消息、最小凭证/关联和 Outbox 要么全部提交，要么全部回滚。重复 key 在并发冲突后读取胜出记录，不产生孤立消息。
- [x] M2.3 实现开始调用的持久边界，以及带有效执行代际校验的结果事务: assistant 结果、终态、会话版本/游标原子提交。
- [x] M2.4 实现按合法轮次读取历史，排除未来排队输入及已确认失败/取消轮次，当前用户消息只加入一次；缓存以版本校验或回源保证正确性。
- [x] M2.5 提供非终态扫描、已完成结果查询及状态投影的仓储能力；活动任务的可恢复输入不能因“已发布”就删除。

**交付物:** 迁移、事务/仓储层及真实 MySQL 集成测试；复用既有聊天内容存储，不另建重复内容库。

**验收门槛:** 跨两个服务对象并发提交同 key，只有一条逻辑请求/用户消息；payload 冲突 409；越权重放被拒绝；任一事务失败不留半成品；最终提交重复执行不多写回复。此阶段尚无消费者闭环，不能单独开放新入口受理真实任务。

## 6. M3: 共享投递与会话执行闭环

### 工作项

- [x] M3.1 实现 Outbox Publisher: 有界批量/重试、发布后记录进度，允许发布成功但未标记时重复投递；多个 Publisher 的领取协议可安全竞争。
- [x] M3.2 实现 Streams consumer group、`XREADGROUP BLOCK`、按执行容量拉取、pending 检查和消费确认；不使用取到即 ACK 或无限本地预取。
- [x] M3.3 接入 M2 的会话执行权和头任务约束；只把可运行 session 交给本地 Pool，等待同 session/配额不能占满 Worker。
- [x] M3.4 Worker 执行前检查持久完成/不确定凭证，执行后提交 SQL 再进行合法 Redis 状态更新和 XACK；失败 ACK 仅在终态已持久化或处理责任已可靠移交后发生。
- [ ] M3.5 明确区分 Provider 正常 EOF 与异常断流；覆盖标题、摘要、主回复及 Agent 多轮调用的恢复边界，不能仅给主回复加去重。
- [x] M3.6 完成正常结束、重复投递、非头任务等待和调用前失联的基础恢复测试；更完整的故障对账在 M4 集成。

**交付物:** API 受理事务到 Redis 投递、Worker 调用、SQL 提交和 XACK 的后台闭环。

**验收门槛:** 同会话第一轮阻塞时第二轮不能进入模型；不同会话可并行；重新投递已完成任务不再调用模型；发布重复不重复落库；旧执行代际不能覆盖当前结果。此时仅允许受控测试，不能把未完成的配额/故障治理暴露到生产流量。

## 7. M4: 异步接口、历史与故障恢复

### 工作项

- [x] M4.1 接入独立生命周期: API 只负责可靠受理，Worker 不继承提交 HTTP Context；任务仍有 deadline、停机管理及资源预算，不成为无管理 goroutine。
- [x] M4.2 最终消息和状态由后台落库，前端通过历史 API 恢复；受理应答丢失时复用原 client ID，禁止以新 key 自动重发。
- [x] M4.3 历史投影 queued/running/completed/failed/uncertain 等必要语义，区分连接错误、Provider 失败、内部最终失败与未知结果，不无限显示生成中。
- [x] M4.4 实现持久事实驱动的恢复扫描: 调用前可安全恢复，可能已调用则查询或 uncertain，已完成只修复投递/状态，不重新调用。
- [x] M4.5 处理“已获取回复、SQL 暂时不可用”: 有界重试保存原结果；进程崩溃且无可靠结果副本时按 uncertain 处理，不通过再次生成伪装恢复。
- [x] M4.6 提供 uncertain 的可审计处理途径并保护后续会话顺序；具体查询、放弃或显式承担风险重试的接口/运维入口经 M1 审阅，不暗中自动重跑。
- [x] M4.7 实现优雅下线、旧 owner 隔离、Redis 状态丢失后的恢复屏障和任务分类重建；如保留流式展示，消费者执行不得被订阅失败阻塞。

**交付物:** 独立受理/后台执行、历史恢复、前端适配、故障恢复流程与基础运行说明。

**验收门槛:** 提交后关闭页面或杀 API，Worker 仍可提交最终结果；更换 API 实例后历史可读；最终提交后丢 ACK 不再生成；外部结果未知可见且阻塞会话；非 EOF 流错误不伪装成功。

M4 通过只代表异步闭环达标，不代表已完成全局容量、附件迁移或多实例上线验收。

## 8. M5: 多实例必要能力

具体实现见 ADR-004、运行说明与检查点。SQL 配额和 MySQL 共享对象是本轮选择的简单基线；未验证的功能等价及上线前置条件仍不勾选。

### M5.A 全局准入与背压

- [x] 明确用户 queued/running 硬上限、受理频率及平台/实际 Provider 账户或凭据组的 quota scope；不以 Provider 名称混淆不同 BYOK 账户。
- [ ] 实现跨实例并发/RPM/TPM 准入、等待/退避和有界预算；覆盖标题、摘要、Agent 循环和 SDK 重试，不只统计聊天任务数。
- [x] 队列上限在受理事务中兑现，限流等待不长期占住 Worker；本轮采用 SQL 配额事实，不随 Redis 投递丢失而重置，SQL 不可用时调用闸门失败关闭，不按实例各自放行。

**验收:** 增加实例不会成倍增加已配置的调用额度；单用户不能占满公共队列；Provider 429 与配额故障不会造成无限重投或隐蔽重复计费。

### M5.B 共享附件与数据生命周期

- [ ] 审阅并实现对象存储后端/抽象；上传、图片读取、摘要、工具读文件、删除会话/用户及清理器全部迁移，不能只改上传接口。
- [ ] 冻结任务附件引用/版本；保护 queued/running/retry_wait/uncertain 任务使用中的文件，配套并发存储配额和幂等清理。
- [x] 旧本机文件复制、校验和映射的工具实现及隔离测试通过，原文件保留；**实际存量迁移尚未执行**。工具完成不代表部署切换或存量附件已全部可读，迁移前不以粘性路由掩盖跨主机不可见。

**验收:** A 上传、B 执行且两者本地磁盘独立时，图片、摘要和工具读取全部成功；排队中附件不会误删；权限和引用版本不因实例切换改变。

### M5.C 运行底座与可观测性

- [ ] 验证 MySQL/Redis 实际持久化、恢复、驱逐/保留策略与版本；任务投递数据与可随意驱逐缓存的资源策略分开管理。
- [ ] readiness 检查迁移版本和必要依赖；配置密钥版本、连接池总预算、日志脱敏及部署角色，禁止把 Provider Key 明文放队列或事件。
- [ ] 从核心链路接入阶段开始收集 request/attempt/sequence/fence 日志及 queue lag、pending age、失败/uncertain、限流、DB 池、附件读取等指标，M5 完成告警与处置入口。

**验收:** 运行人员可以定位悬挂任务并按安全流程恢复；重建 Redis 不直接无条件重放全部任务；观测数据不泄漏凭据或无界用户标签。

## 9. M6: 综合验收与上线

- [ ] M6.1 在真实 MySQL、Redis、共享附件环境运行至少两个 API/Worker 实例，并使用独立本地磁盘、可控 mock Provider，验证非粘性路由下的正确性。
- [ ] M6.2 覆盖受理提交前后、发布后未标记、调用前后、最终提交后未 ACK、旧 Worker 恢复、Redis 数据丢失及 DB 暂停等故障点。
- [x] M6.3 使用 channel/barrier 或可控时钟断言模型进入次数、消息行数与顺序；执行 Go 单元/集成/race 测试。Race 通过不能替代业务并发测试。
- [ ] M6.4 压测同会话热点、多会话、多用户、长回复及附件任务，记录受理/等待 P95/P99、完成延迟、DB 负载、内存和上游成本；据此确定容量与超时预算。
- [ ] M6.5 采用扩展式迁移、固定用户/会话灰度和旧任务排空；同一会话不能由新旧两条链路同时写入，不能用真实模型“双执行”验证影子流量。
- [ ] M6.6 演练回滚到兼容新持久事实的版本；不删除待执行任务、不回滚到忽略请求凭证的旧 Worker、不提前删除旧附件。
- [ ] M6.7 记录实测恢复时间、存储可靠性边界、告警和人工处置步骤，评审通过后才开放多实例生产流量。

**交付物:** 自动化验收报告、容量基线、迁移/灰度/回滚手册、运行看板与明确发布结论。

**发布门槛:** M2-M5 全部达标，关键故障用例通过，存量数据/附件迁移有可验证记录。仅部署两个进程、增加 Worker 数或开启 AOF 不算通过。

## 10. M7: 后续优化，按数据触发

- 更细的 Provider 熔断与故障隔离、用户调度公平性优化、投递批处理及成本策略。
- 只有观测到实际瓶颈后，才讨论更复杂的 MQ、分区方案、独立扩缩和自动化容量治理。
- 在线流式体验可优化为 delta、有界缓冲或有限快照，但不改变后台独立完成及 MySQL 历史事实源。
- 每项优化保留现有幂等、会话顺序、执行权及 unknown-result 约束，不以吞吐为由绕过它们。

以上是后续候选，不属于本轮批准的实施细节，也没有预设排期。

## 11. 风险与决策跟踪

| 待细化项 | 必须在哪之前关闭 | 不允许的默认假设 |
| --- | --- | --- |
| 最小凭证物理结构及 SQL 版本迁移 | M2 实施前 | 把改建表语句当作升级已有数据库 |
| owner/lease/fence 与 SQL/Redis 提交协议 | M3 实施前 | 仅凭 Redis 锁或 pending idle 判断执行权 |
| uncertain 查询/放弃/风险重试的操作语义 | M4 验收前 | 无 ACK 就自动重新调用上游 |
| 在线 SSE 保留方式、旧接口兼容 | M4 接口切换前 | 浏览器收到 done 才算业务完成 |
| quota scope、预算、退避和附件存储后端 | M5 对应实现前 | 本机 MaxWorkers 等于集群全局限额；本地路径跨主机可用 |
| MySQL/Redis RPO、任务恢复目标和容量 SLO | M6 上线评审前 | 开启 AOF 就零丢失；无压测即可承诺 QPS |
