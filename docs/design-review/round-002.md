## Q1: 是否采用 SQL-first + 轻量 Outbox + Redis Streams pull？

**推荐答案:** 采用。保留现有聊天内容的 MySQL 持久化，在受理事务中同时写用户消息、请求关联/最小凭证和 outbox；Worker 主动阻塞拉取，回复可靠提交后才 XACK。

不预设完整 `chat_requests` 表，但接受最小持久执行事实: 除结果唯一关联外，还要知道调用是否可能已开始以及最终处置，才能在 Redis 丢状态后避免盲目重跑。物理上放在现有表还是小型凭证表尚未决定，不用换表名掩盖同一份复杂度。

请求/流式中间状态可以放 Redis/内存；恢复所必需的事实不能只放那里。代价是少量 SQL 写入和一个发布/对账流程，性能未压测。

用户答复: 接受推荐。采用 SQL-first + 轻量 Outbox + Redis Streams pull，接受最小持久执行/结果凭证，不预设完整请求表。

后续展开: 物理 schema、事务边界、Outbox 保留、持久调用标记、Redis owner/epoch 与 SQL 最终提交的配合。

## Q2: 同会话允许排队吗？不确定态是否阻塞后续执行？

**推荐答案:** 正常时允许有界排队，按服务端受理序列串行；不同会话在全局/用户额度内并行。前一轮处于 uncertain 时，该会话后续任务保留但不执行，并暂拒新增受理，直到查回结果或用户明确选择处理方式。

已确认失败/取消的轮次保留在界面，但不加入后续有效模型历史；确认其处置和执行权失效后可继续后面的任务。用户要重试 uncertain，应作为显式风险操作处理，不能由 pending 回收默默触发；具体重试身份/队列位置留到下轮。

代价: 保守阻塞可能让该会话等待人工处理，但避免在上下文尚未确定时继续生成。等待中的任务可以显式取消；首版具体排队上限后续结合容量预算决定。

用户答复: 接受推荐。同会话有界排队、串行执行，uncertain 阻塞该会话后续执行并暂拒新增；已确认失败/取消的轮次不进入有效模型历史。

后续展开: 会话游标、队列上限、上下文组装及 uncertain 的显式恢复/取消操作。

## Q3: 幂等凭证是否随会话保留？

**推荐答案:** 最小幂等凭证随会话保留，而非回复完成就删除或只保留几分钟。相同 key、相同规范化 payload 返回原请求/状态；相同 key、不同内容、模型或附件语义返回 409，不覆盖、不自动另跑。

大任务 envelope、Redis 投递历史、草稿不要求同寿命；请求到达已确认终态且不再需要恢复后可以按策略清理，但保留 key/hash/终态及结果关联。删除会话时执行统一删除政策，不能靠旧 key 重建已删除资源。

代价: 每轮保留一份紧凑身份/结果凭证，不需要保存另一份完整聊天正文。具体 TTL/归档策略只有在未来改变这项契约时再引入。

用户答复: 接受推荐。最小幂等凭证随会话保留；同 key 同 payload 返回原请求，同 key 不同 payload 返回 409。

后续展开: key 规范化、唯一索引、payload hash、历史数据迁移和用户显式重新生成的身份。

## Q4: 浏览器断连是否继续任务？

**推荐答案:** 已可靠受理后，即使刷新、断网或 SSE Gateway 下线，任务继续；用户通过原请求 ID 查询/重新订阅。停止生成必须是显式取消，而不是关闭连接的隐含副作用。

取消和完成竞争时返回真实终态；不能确认上游停止时仍按 uncertain 规则处理。后台继续执行可能产生费用，前端应提示这一语义。

本轮只决定生命周期，不要求现在选定 POST 202、旧 SSE 兼容方式或逐 token 回放机制；这些属于下一层协议设计。

用户答复: 前端提交后后端应自行完成，提交连接与执行生命周期解耦；用户后续通过 MySQL 历史恢复。用户提出“除非是 API 供应商的问题才显示有问题”，其中前端断连不属于业务失败已确认。后续第 3 轮已澄清并接受：短暂内部故障后台恢复，内部最终失败或结果不确定也如实展示，不静默隐藏非供应商故障。

确认范围: 不再追问断连是否继续执行；SSE/在线进度是可选观察渠道，不是完成条件。恢复历史指前端通过受鉴权的后端 API 读取 MySQL，不是浏览器直连数据库。显式取消的产品入口尚未批准，不因解耦默认增加“停止生成”功能。

后续展开: 受理响应和历史读取中的任务状态；在线 SSE 如保留则独立订阅，不为历史恢复强制实现逐 token 重放。任务删除/取消和执行竞争的安全边界在执行协议中处理，独立取消 UI 可另行决定。
