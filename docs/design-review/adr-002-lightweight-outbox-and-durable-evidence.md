# ADR-002: 轻量 Outbox 与最小持久凭证

- 状态: **Accepted，框架层已批准；物理 schema 与执行协议待细化**。
- 日期: 2026-10-11。
- 确认依据: 用户在第 2 轮明确接受 Q1-Q3。批准范围为本 ADR 的框架、同会话排队和幂等生命周期，不代表尚未设计的具体字段或代码实施已获批准。
- 范围: 确定职责与必须保留的信息，不给出 DDL，不实施代码，不预先承诺性能。

## 1. 已接受的方向

**SQL-first 可靠受理 + 小型事务 Outbox + Redis Streams 阻塞拉取 + 最小持久执行/结果凭证。**

这是上一份 issue 中 Redis/MQ 路线的收敛版本，不再默认先实现 MySQL 任务领取队列，也不要求引入覆盖全部运行状态的完整 `chat_requests` 表。

| 组件 | 职责 | 不承担什么 |
| --- | --- | --- |
| MySQL 消息及最小凭证 | 请求去重、受理/外部调用边界、最终结果和终态的可恢复事实；必要的执行代际校验 | token 级日志、常态任务抢占式轮询队列 |
| MySQL Outbox | 和用户消息同事务记录可恢复的投递意图；Publisher 可重复发布 | 凭 published 字段推断模型是否执行 |
| Redis Streams | 共享投递、阻塞领取、pending/ACK、限量预取；丢失时从 SQL 事实恢复调度信号 | 唯一完成凭证、自动会话串行、exactly-once 模型调用 |
| 本机内存/Worker Pool | 热缓存、本机并发上限、临时流式缓冲及执行器 | 权威幂等状态和唯一任务副本 |

内存模型可以复用，但其内容必须允许丢弃/回源。最小持久凭证放在现有消息、紧凑专表还是组合结构，由后续 schema 设计决定。

## 2. 为什么仍需少量执行事实，不能只增加最终结果 ID

已接受的两个要求会产生一个约束:

1. Redis 的投递/状态丢失后，要能判断是否需要恢复已受理任务。
2. 上游可能已计费时，不能在不知道以前执行情况的前提下自动重跑。

若 SQL 里只有用户消息和 outbox 的 published 标志，Redis 丢失后会看到“用户消息存在、无最终回复”。这可能是尚未执行，也可能是模型已执行但结果丢失，不能直接重投后调用模型。

因此至少需要保留请求身份、外部调用边界和已知终态。**不建完整请求表不等于完全不保存请求执行信息。**若这些字段最终已经承担大部分状态机功能，应如实称为紧凑执行凭证，不能仅改名叫 outbox 来掩盖成本。

## 3. 需要持久化的最小信息类别

以下是逻辑信息，不要求全部落在同一张表，也不代表已确定字段数量:

- 请求身份: user/session/client ID、服务端 request ID、payload hash，完成后也能判重。
- 可恢复输入: 用户消息引用、Provider/解析后 model、影响语义的生成配置、冻结附件引用及版本；不存 API Key 明文，不复制整份聊天历史。
- 顺序/有效性: 会话序列，以及最终提交事务能够验证的有效 owner/epoch 或等价机制。仅在 Redis 查锁后再无条件写 SQL 存在检查与使用之间的竞态。
- 调用边界: 执行前的持久意图/可能已发送标记。标记提交后才允许发起外部调用；其后宕机一律先按不确定处理，不能假定没有执行。
- 最终处置: assistant 消息引用、已确认失败/取消/不确定等必要状态，避免失败任务 ACK 后只在易失内存留下标记。
- 投递元信息: 事件 ID/版本、发布进度及重试时间，用于 Outbox Publisher 而不是用于证明执行完成。

一次聊天可能有标题、摘要、Agent 多轮调用。各外部调用也必须受统一许可/恢复策略约束；首版可以保守地在任一调用可能已发出后将整次失联执行标为 uncertain，但不能假称只标主回复就覆盖全部副作用。精细的子操作凭证是否必要留到执行协议设计。

## 4. 候选执行链路

```text
API
  |
  +-- MySQL 短事务
  |     校验幂等/归属及受理上限
  |     写用户消息 + 最小凭证/关联 + outbox
  |     提交后才确认受理
  |
Publisher -- XADD --> Redis Streams
                         |
Worker -- XREADGROUP BLOCK --+  # 进入 PEL，不是完成
  |
  +-- 查持久事实；已有终态则不重复调用
  +-- 验证会话顺序、有效执行权和全局额度
  +-- 提交外部调用意图，再发起 LLM 请求
  +-- MySQL 短事务: 校验执行权 + 回复/终态 + 会话推进
  +-- Redis 状态修复/完成确认 + XACK
  +-- 前端通过事件或查询观察结果，不参与提交判定
```

不在外部模型执行期间持有 SQL 事务。最终持久化由执行服务完成，不再依赖原 HTTP Handler 是否存活。SQL 和 Redis 之间没有原子事务，以 SQL 可恢复事实和幂等重投闭合窗口。

调用意图与网络发送仍非原子: 可能“记了意图但没发出”。该设计有意偏向保守 uncertain，代价是偶尔需要人工恢复，而不是通过隐蔽重试冒重复计费风险。

## 5. Outbox 的清理与 Redis 丢失后的对账

- Publisher 的“已发布”只证明曾尝试成功投递，不能在仍无业务终态时删除唯一可恢复输入。活动任务保留 envelope，或保证它可从其他持久事实完整重建。
- Redis 丢失后先建立恢复屏障，暂停新增上游调用并处理可能仍在运行的旧所有者，再重建队列/配额；不能立即把所有“无回复”消息重新执行。
- 恢复扫描依据持久调用边界分流: 未开始且执行权可安全取得的可补投；可能已发出调用的查上游或进入 uncertain；已有终态的仅修复 Redis 状态/确认，不再执行。
- 终态请求可以清理不再需要的大 envelope 和投递历史，但按第 2 轮 Q3 已接受的规则，最小幂等摘要与结果关联随会话保留，不能随着 XACK 一起删除。
- Redis 并非所有功能都能靠 Outbox 恢复: 在途 Provider 配额等需要保守等待/对账；中间 token 可按产品约定丢失并恢复快照。

本方案把 Redis 丢投递的恢复依据留在 SQL，不保证 SQL 自身灾难丢失时也零丢失。MySQL 持久性、备份、故障切换和恢复时间仍需要后续配置验证与演练。

## 6. 轻量的边界与代价

不保存每个 token、不复制全历史、不先做 DB 常态任务调度，降低的是系统范围；仍然存在受理、调用边界及终态的持久写入。Outbox Publisher 也要扫描 SQL，不能称为“完全不轮询数据库”。

实际写放大、索引成本与响应时延必须压测，不能凭表名或字段数量判定比完整请求表快多少。如果最小凭证不断膨胀，评审应选择清晰的小表，而不是为坚持“不建表”把所有信息塞进 messages JSON。

## 7. 已确认与后续边界

第 2 轮已确认本框架；最小幂等凭证随会话保留，不能随着 XACK 删除。同会话正常有界排队，uncertain 阻塞后续执行；已确认失败/取消的轮次不进入有效模型历史。

前端与后台任务生命周期独立，最终回复由 Worker/执行服务写 MySQL；后续历史读取不依赖原连接。具体说明见 `adr-003-async-execution-and-history.md`。

后续细化 SQL/Redis 字段、lease/epoch、回收与具体接口；框架确认不等于开始数据库迁移或代码实施。第 3 轮已确认错误展示原则：短暂内部故障后台恢复，最终失败/不确定状态在历史中如实展示，详见 `adr-003-async-execution-and-history.md`。
