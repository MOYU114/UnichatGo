# 第 1 轮: 先定保证边界，再定存储框架

状态: **已确认，三项推荐均获接受**。日期: 2026-10-11。

确认依据: 用户回复“你的推荐都可以接受，先按照你的思路来”。此确认对应本轮 Q1-Q3，不代表后续具体架构、容量参数或代码实施已获批准。

本轮三个问题都是可独立作出的产品/工程取舍。请求事实放哪里、是否需要 Outbox、Redis 参数和回收细节依赖这些回答，留到后续轮次。

## Q1: 已确认受理的任务，承诺恢复到什么程度？

当接口已经告诉用户“已受理”后，你希望对 API/Worker 崩溃提供怎样的恢复承诺？对 Redis 自身故障导致的已确认写入丢失，又愿意承担多大的窗口？不要把进程崩溃和 Redis 持久存储灾难混成同一件事。

**推荐答案:** API/Worker 崩溃不能丢已受理任务；首版也不应默许 Redis 丢了就只能让用户重发。先以有可恢复依据为目标；如果选 Redis-first，需要再明确其持久化/故障切换承诺和剩余 RPO，而不是仅凭 AOF 宣称零丢失。

用户答复: 接受推荐。API/Worker 崩溃不能丢已受理任务；Redis 故障需要恢复依据或明确的丢失预算。具体 Redis/MySQL 持久化与故障切换 RPO 尚未测定，不能据此承诺任意灾难下零丢失。

影响: 决定 Redis 能否作为唯一受理事实源，以及是否需要 SQL 补投/恢复依据。

## Q2: 你是否允许“最小 SQL 改造”，而不是完整请求表？

你的约束是否允许在消息中增加稳定请求关联、相应唯一约束，并调整最终结果的事务边界？这与新建一套完整请求状态表是不同的成本，也与强制每个 token 落库无关。

**推荐答案:** 不预设完整 `chat_requests` 表；允许少量请求关联字段、唯一键和必要事务修改，用于识别“这条任务的结果已经提交”。本机内存继续用于热缓存，不继续作为唯一幂等/完成状态。

用户答复: 接受推荐。不预设完整 `chat_requests` 表；允许最小关联字段、唯一键与必要事务改造，内存保留为缓存，不独自承担幂等和完成状态。

影响: 决定如何封闭“SQL 已完成、Redis 未 ACK”后的重复投递窗口；能否给 Redis 丢失的终态提供恢复凭证。

## Q3: 上游可能已计费但结果未知时，允许自动重跑吗？

模型请求已经发出，Worker 崩溃，系统没有拿到最终结果。此时队列只能证明没收到 ACK，不能证明 Provider 没执行。你是否授权后台自动再次调用，并承担可能的重复计费？

**推荐答案:** 默认不盲目重跑。Provider 有可靠幂等/查询能力时优先恢复；否则记为 uncertain，由用户显式决定是否重试。调用发出前的可证实失败才自动安全重试。

用户答复: 接受推荐。上游结果不确定时不盲目自动重跑；优先查询/恢复，否则记录 uncertain 并由用户明确决定是否重试。

影响: 决定 pending reclaim 能否直接执行，还是必须先查结果/进入不确定态；决定人工恢复入口和前端提示。
