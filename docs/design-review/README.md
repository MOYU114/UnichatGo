# 水平扩容方案对账

日期: 2026-10-12。状态: 用户已授权实施；ADR-004 详细协议经独立审阅，核心异步代码已实现并开展真实 MySQL/Redis 验证；M3-M6 完整验收尚未完成。

这里的“对账”指架构观点、代码事实和决策的核对；不是已经实现的数据库/队列自动对账程序。本文档集保留原始讨论；本轮已进入代码、迁移、前端与测试实施。

维护约定: 目录统一为 `docs/design-review/`，文件名均为英文；文档正文可以使用中文。该目录是原讨论目录的重命名，不另留一份内容副本。

## 当前共识与分歧

| 分类 | 当前记录 |
| --- | --- |
| 用户目标 | 先确认实现框架，降低改造复杂度，不希望默认引入完整 MySQL 请求表 |
| 已接受的框架 | SQL-first + 轻量 Outbox + Redis Streams 阻塞 pull；SQL 保留最小持久事实，内存保留为缓存 |
| 第 1 轮已接受 | 已受理任务需要恢复依据；允许最小 SQL 字段/唯一键/事务改造，内存只是缓存；上游结果不确定时不自动重跑 |
| 第 2 轮已接受 | 同会话有界排队，uncertain 阻塞后续；幂等凭证随会话保留、payload 冲突返回 409；前端连接与后台执行独立，最终历史从 MySQL 恢复 |
| 第 3 轮已接受 | 连接断开不算任务失败；短暂内部故障后台恢复；供应商失败、内部最终失败及 uncertain 在历史中如实展示并区分归因 |
| 本轮细化 | ADR-004 定义紧凑凭证、fence/lease、SQL 配额、观察式历史与共享对象；辅助/Agent 调用等价和实际灾难 RPO 仍未验收 |
| 需要纠正的术语 | Redis 队列不天然是事务 Outbox；当前 SSE `ack`、队列领取和队列 ACK 是三个不同事件 |
| 当前 ACK 原则 | 领取仅进入 pending；SQL 有效代际提交终态或可靠交接后才确认；Outbox generation CAS 和持久调用边界保护恢复，不等待浏览器 |

上一份 issue 的 MySQL 请求表路线仍只是建议，本轮不将其当作既定约束，也不覆写原文以制造已达成共识的印象。

## 设计树

```text
目标: 简化实现，同时明确水平扩容实际保证
|
+-- R1: 已受理任务有恢复依据，不默许 Redis 丢失后只能重发 [已接受]
+-- R2: 允许最小 SQL 改造，内存降为缓存 [已接受]
+-- R3: 上游结果不确定时不自动再次调用 [已接受]
|
+-- 第 2 轮 [已接受]
|   +-- Q1: SQL-first + 轻量 Outbox + 最小持久凭证 + Streams pull
|   +-- Q2: 同会话排队，以及 uncertain 阻塞后续执行的规则
|   +-- Q3: 幂等记录随会话保留，同 key 不同 payload 拒绝
|   +-- Q4: 后台独立执行，浏览器从 MySQL 历史恢复；断连不是任务失败
|
+-- 第 3 轮 [已接受]
|   +-- Q1: 短暂内部故障后台恢复，所有最终失败/不确定状态如实可见
|
+-- 后续: 按本轮回答重新展开，不提前固定
    +-- 物理字段、状态迁移、事务边界及投递/恢复扫描
    +-- session 序列、owner/lease/fence、上下文与回收
    +-- 全局配额、用户额度与退避
    +-- 受理/历史 API；在线 SSE 是可选观察渠道，不是恢复历史的前提
    +-- Redis 配置、裁剪、迁移、故障测试
    +-- 共享附件与清理
```

下一轮根据已接受的前提展开，不能反复追问已定原则，也不能一次追问尚未确定前提下的所有实现细节。环境事实由助手核对，不能让用户猜现有代码、实际调用顺序或配置。

2026-10-11 的历史轮次只读复核了请求 Context、最终落库与历史查询边界，结论保存在 ADR-003；当时只记录用户确认。2026-10-12 的代码与运行验证见本文末尾的实施索引。

## 推进规则

1. 用户观点、已验证事实、推荐方案、批准决策分别记录。
2. 每轮更新答复与待决项；已定的决策注明日期和理由。
3. `ADR` 在达成共识前保持 Proposed；不能因为文档写得具体就视为已获批准。
4. 最新实施授权允许与已接受语义一致的技术细节在设计和独立审阅后推进；重大产品变化仍需明确授权。
