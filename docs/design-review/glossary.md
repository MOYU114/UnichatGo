# 术语与领域边界

状态: 工作词汇表，随讨论修订。日期: 2026-10-11。

| 术语 | 在本项目讨论中的含义 | 不等于什么 |
| --- | --- | --- |
| 逻辑请求 | 用户的一次生成意图，网络重发应仍对应同一请求 | 一次 HTTP 连接或一次 Worker 执行 |
| `client_msg_id` | 客户端为一次生成意图分配、重发时复用的不透明 ID；必须带用户和会话命名空间 | 授权凭证；换 ID 就仍是同一幂等请求 |
| `request_id` | 服务端稳定请求标识，用于结果关联、恢复和查询；可以只是新增关联字段，不必然要求完整请求表 | Redis Stream entry ID |
| 用户/助手消息 | 当前已经持久化到 SQL 的聊天内容 | 能完整恢复任务的记录；现表缺少请求 ID、模型、附件快照及执行状态 |
| 任务 envelope | Worker 恢复执行所需的版本化描述，包括请求标识、用户/会话、输入引用、Provider/model、附件等 | 本地函数、`context.Context`、回调或 API Key 明文 |
| 内存缓存 | 每个进程自己的 history/resource/map，可丢失并重建 | 跨实例唯一性或持久的完成凭证 |
| Redis 共享状态 | 多实例可读的幂等映射、任务状态、lease 等 | 仅凭“共享”就具备无限期持久性和灾难零丢失 |
| Redis Stream | 追加日志/队列载体，生产者 `XADD`，消费者可按游标/消费组读取 | 事务 Outbox 或模型执行状态机 |
| 事务 Outbox | 将业务事实与待发布事件在同一事务系统内提交，再由发布器投递 | MySQL 写一遍、Redis 再写一遍；两个独立系统的写入并不自动原子 |
| Pull / 阻塞拉取 | Worker 有容量时调用 `XREADGROUP ... BLOCK` 等待 Redis 返回任务 | 忙循环轮询；或“不需要恢复、幂等和 ACK” |
| PEL / pending | 消费组已经投递但还未 `XACK` 的 entry；不使用 `NOACK` 时形成 | 已完成；永久独占锁；同 session 串行 |
| execution owner | 当前获准执行某请求/会话的 Worker，通常结合 lease/epoch 判断有效性 | 收到 entry 就永远有执行权 |
| 队列 `XACK` | 从指定消费组的 pending 集合中移除 entry，结束该次投递的待确认状态 | 从 Stream 删除消息；自动写业务成功；前端确认收到了答案 |
| SSE `ack` | 当前接口中的“用户消息已保存”通知 | Redis ACK；当前发送此事件时任务还没有进入 Worker |
| business completed | 最终结果及必要关联信息已提交，之后可恢复查询且不会重复写入 | 模型回调结束；浏览器收到 `done` |
| 异步受理边界 | 后端确认可靠受理后，任务由独立生命周期负责；若确认响应丢失，客户端用同一幂等键核对 | 浏览器本地调用 fetch 就保证后端已受理 |
| 历史恢复 | 浏览器通过鉴权后的后端历史 API 读取 MySQL 中已提交的消息及必要状态 | 浏览器直连 MySQL；仅有用户消息就证明生成成功 |
| 连接错误 | 提交或订阅的网络链路中断，可能需要核对受理状态或重新读取历史 | 自动取消任务，或自动创建新的生成请求 |
| 任务失败/不确定 | 后台执行无法完成、无法确认外部结果或无法持久提交的业务状态 | 所有情况都归因于 API 供应商，或无限显示正在生成 |
| 幂等完成凭证 | 能识别“该 request 的结果已提交”的持久标识，允许重投直接结束 | 只在当前进程有效、完成后删除的 map entry |
| 最小持久执行凭证 | 记录请求身份、是否可能已开始外部调用、当前有效执行代际和最终处置的恢复依据；物理上可附在消息、操作凭证或专表 | 完整复制聊天历史；单凭 outbox 的 published 标志判断是否执行 |
| published / 已发布 | Publisher 已观察到一次 Redis 投递成功，后续仍可能重复发布或由恢复扫描补投 | 模型已调用、结果已提交，或 Redis 后来绝不会丢数据 |
| reclaim / 回收 | 对疑似失联消费者的 pending entry 进行检查和接管；Streams 可用 `XAUTOCLAIM` 等机制 | 单看 idle 时间就证明模型已停止，可以无条件重跑 |
| fencing / epoch | 单调执行代际，用来拒绝旧所有者写入或输出 | 撤销已经发到外部 Provider 的网络请求 |
| uncertain / 不确定态 | 外部模型可能已执行或计费，但本系统无法确认其结果 | 可以安全重试的普通失败 |
| RPO | 故障恢复后可接受丢失多少已确认数据 | “开了 AOF 就天然为零” |
| 灾难对账 | 从另一个持久依据识别并修复丢投递、状态不一致等问题 | 扫描当前聊天正文就必然能恢复 Provider/model/附件及请求身份 |

## 三种“完成”分别属于谁

```text
业务存储: 最终回复已可靠提交
Redis 消费组: 本 entry 的处理责任已完成或可靠移交，允许 XACK
浏览器: 观察到完成事件，或随后通过状态/历史接口查询到完成结果
```

三者不可能靠“最后调一次 Redis”自动组成一个原子事务。方案必须允许事件重复、通知丢失和任务重投，同时明确每种情况如何查询与收敛。

## 本轮建模约束

- 请求、一次执行 attempt、队列 entry 分开命名。同一请求可能因安全重试经历多次执行或多条投递。
- 可以不建完整 `chat_requests` 表；但如果承诺跨重启和跨实例幂等，必须明确稳定请求身份和完成凭证放在哪里、保留多久、丢失后如何处理。
- 保留内存缓存与保留“只靠内存判断执行状态”是两个不同决策。
