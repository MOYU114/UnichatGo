# ADR-004: Async execution protocol

Date: 2026-10-12. Status: implementation details independently reviewed under the user's M1-M6 execution authorization. Review findings and required verification are recorded in `review-001.md`; design acceptance is not runtime acceptance.

## Scope and physical storage

The accepted ADR-002/003 semantics remain unchanged. A compact `execution_evidence` table is clearer than nullable state-machine fields on every historical message. It references existing message bodies, never copies full history or tokens. `execution_sessions` holds acceptance sequence and completion cursor; `execution_outbox` holds durable delivery intent. This is not a SQL worker claim queue: normal execution is triggered only by Redis Streams.

- Evidence: UUID request ID; user/session/client ID (binary, bounded); canonical payload hash; user/assistant message IDs; server sequence; provider/model; encrypted credential snapshot/version and non-secret quota scope; immutable attachment IDs; queued/running/completed/failed/uncertain state; error code; owner, monotonic fence, lease deadline, call-started marker; creation/deadline timestamps.
- Unique indexes: `(user_id, session_id, client_id)`, `(session_id, sequence)`, user message ID, nullable assistant message ID. Session and user foreign keys preserve ownership and cascading retention.
- Outbox: request ID primary key, next publish time and publish count; retain until terminal or audited uncertain handoff. Delivery envelope contains only request ID, never credentials/content.
- Execution session: persist a `legacy_max_message_id` cutoff on its first acceptance. Every later context read includes this immutable legacy prefix and only completed earlier async user/assistant pairs. Async messages must never be inferred to be legacy just because a join is absent.
- Payload identity: hash a canonical client semantic payload (trimmed content, normalized explicit provider/model selection and sorted unique attachment IDs), independently of current credentials, defaults or file availability. Attachment lists have set semantics and use the same deterministic order for hashing and execution. Omitted/empty attachment lists both mean no attachment; there is no implicit cached attachment reuse. Canonicalization is a versioned protocol contract that must not change for retained keys without compatible comparison. Compare an existing key before resolving mutable dependencies. Freeze the resolved model, endpoint, output budget and encrypted credential version only for new acceptance.
- Versioned additive migration uses a schema version table and MySQL migration advisory lock. Existing messages retain their IDs; legacy context is read only before the session's first asynchronous acceptance. SQLite remains a legacy single-node development mode, not a substitute for MySQL tests.

## Lock order and transaction boundaries

1. Accept: lock user row then owned session row; initialize/lock execution session; check existing key before quota/dependency/input availability checks. Same hash returns the original receipt, different hash returns 409. Auth and session ownership always precede the lookup. Enforce user/session queue and frequency bounds, freeze inputs, insert user message/evidence/outbox and increment sequence atomically. Commit before 202.
2. Claim: every mutating transaction follows user, session, evidence, then lexically sorted quota scopes; delete/cleanup/renew/resolve use the same applicable order. Only the first non-terminal sequence can claim. SQL clock determines leases. Increment fence and assign owner for a bounded lease. Non-head/temporarily limited entries are durably delayed through outbox before their delivery is ACKed; they do not occupy a worker waiting for the head.
3. Call boundary: atomically reserve all quota scopes and persist `call_started` under owner/fence/live-lease condition before ANY external call. A failed scope reservation rolls back the entire transaction. All upstream calls, including auxiliary calls, require the same quota gate and boundary. No transaction spans network I/O.
4. Complete: lock the session/evidence and require the same owner/fence/live lease. Insert assistant message, terminal evidence and session cursor in one transaction. Duplicate terminal delivery never invokes the model. No stale cache writes: async context is assembled from SQL completed prior turns plus current input exactly once, excluding all future, failed and uncertain turns.
5. ACK: only after a durable terminal/uncertain fact or durable delayed outbox handoff. A stale worker must re-read durable facts; XACK alone never authorizes completion. The stream is a delivery mechanism, SQL is the authority.

## Recovery and scheduling

- Publisher may duplicate XADD after lost publish marking; bounded republishing of durable active outbox rows restores lost Redis signals. Consumers use capacity-sized blocking reads plus bounded XAUTOCLAIM. Never trim unresolved entries; ACKed entries may be deleted.
- Outbox scheduling has a monotonic generation. Publisher captures generation before XADD and marks progress only with `WHERE generation = captured_generation`; durable consumer deferral increments it. Thus late publisher marking cannot overwrite a newer delayed handoff. Failed CAS is harmless; the durable row remains eligible according to its newer schedule. Multiple publishers may duplicate delivery but may not erase each other's recovery intent.
- Expired pre-call ownership is safe to fence and return to queued. Expired post-boundary execution becomes uncertain, never automatically invoked again. Unknown upstream transport/stream outcomes are uncertain; explicit rejection is provider_failed. Final response save retries reuse the original response and have a finite budget.
- A SQL-backed global quota ledger is chosen over volatile Redis quota counters for the first implementation. It reserves concurrency, RPM and conservative token budgets per platform/user/actual credential group before each call. Scope identity uses a protected fingerprint of the actual credential, not provider name or user ID alone; configured aliases must group multiple credentials sharing an upstream account. Reservations are attached to request/fence and stale owners cannot release another generation's permits. Permits initially last through the immutable task deadline plus safety grace, independently of the shorter renewable worker lease; this avoids a separate permit-renew race. Any future short renewable permit must renew atomically with execution ownership. RPM/TPM use SQL time and conservative rolling-window reservations, never refunds for possibly consumed work.
- Redis loss cannot reset SQL quota or execution ownership. Rebuild reads and classifies persistent boundaries before any new call, never grants permissions merely because the stream/group was recreated. Execution lease expiry fences local writes but does not prove an upstream call stopped: uncertain concurrency reservations remain quarantined through at least the bounded call deadline plus configured safety grace. Timeout/cancellation cannot guarantee physical upstream cancellation; this limitation is explicit and production quota sizing must allow it. SQL is not used as the normal task claim queue.
- Task deadline and graceful shutdown are bounded; stopping API has no effect on separate workers. Worker drain stops new pulls and retains leases while finishing; forced stop is recovered using call boundaries.
- Uncertain blocks later execution/new acceptance. Authenticated owner may explicitly abandon with a nonempty reason. Audit actor/reason/old fence; increment fence and advance only after the old lease has expired. No automatic risk retry endpoint: after abandonment the user may explicitly create a new request, with duplicate-charge warning.
- Abandonment records a failed terminal state with `abandoned_uncertain`, retaining the original uncertain fact and audit, not claiming the upstream was cancelled or succeeded. It does not release quarantined external-call quota prematurely. Expired queued/pre-call tasks become durable internal failures; an expired post-call boundary becomes uncertain. These transitions are recovered after DB availability returns rather than leaving permanent running states.

## API and rollout

- Async mode is explicit and MySQL-only. Role is `api`, `worker` or `all`. A deployment-wide write gate must prevent old binaries/legacy handlers writing async sessions; rollout requires draining old processes before switching. Rollback means a compatible async binary with acceptance paused, never deleting evidence or downgrading to legacy workers.
- `POST /api/users/:id/conversation/msg`: 202 receipt `{request_id,user_message_id,sequence,state}` (200 for replay); 409 payload conflict/uncertain; 422 deterministically unsupported/over-budget input; 429 bounded admission; 503 dependency unavailable. Old SSE is retained only when async mode is disabled; never both for one async session. Empty history is an array in both modes; frontend accepts legacy `messages: null` only after confirming legacy mode, never for async history.
- History adds `requests` containing safe receipt/status projection; no owner, secrets or envelope. `POST .../requests/:request_id/resolve` supports only explicit abandon with reason. DB outage returns 503, not manufactured task status.
- Frontend uses one persisted client ID and frozen payload until definitive acceptance/rejection. Connection failure is `acceptance_unknown`, not a task failure. History polling is observational, bounded/backed off, cancellable on navigation; refresh recovers from SQL. Queued/running/failed/uncertain are visible; uncertain blocks sending and offers audited abandonment.

## Attachments and external integrations

Immutable, content-hashed shared objects are referenced by owned metadata, not arbitrary local paths. The bounded first backend may store objects in MySQL to avoid introducing an unconfigured object service; the interface permits an S3 adapter later. This deliberately trades DB I/O/backup size for a small, shared, transactional baseline. Per-user storage admission is serialized, active evidence pins attachments, and cleanup/delete use the same lock order as acceptance. Existing local files require an explicit copy-and-hash migration; never silently use sticky routing.

User/session deletion is rejected while queued, running or unresolved uncertain evidence exists, rather than cascading away the only call boundary, quota owner or attachment pin. Explicit abandonment permits later deletion but quota quarantine must survive any parent cascade until its safe release time. Completion/delete and pin cleanup serialize on the same user/session locks; no deleted session can be resurrected by a stale worker. Legacy file migration verifies ownership, size and hash and updates metadata transactionally; source files remain until an explicit verified cleanup.

Provider adapters must disable hidden retries and detect incomplete responses. Unsupported provider/tool paths must fail closed before acceptance rather than silently bypass quota/boundaries. Title generation may use a deterministic local title to avoid unnecessary paid side effects. Any feature not yet supported is documented and blocks feature parity acceptance, not claimed complete.

The bounded async adapter uses one non-streaming raw HTTP call with a frozen endpoint/output budget, no redirects and no automatic retries. A complete JSON response plus a recognized success finish marker is required for success. Missing finish markers, incomplete response transfer/JSON, transport failures and ambiguous server errors are uncertain; explicit provider rejection is failed. A completely received, structurally valid response with OpenAI `length`, Claude `max_tokens`, or Gemini `MAX_TOKENS` confirms termination at the output budget and is `failed / provider_output_truncated`, not uncertain. The partial output is not saved as a successful assistant message and the failed turn is excluded from later model context; after committing failure, the next queued turn may run. No automatic regeneration or output-budget increase occurs. A transport failure stays uncertain even if its partial bytes contain one of these markers. This clarification follows the user's review of the earlier overly broad word "truncation" and changes no unknown-result isolation rule.

Image reservation uses `32768 + 8192 * ceil(width/512) * ceil(height/512)` per validated static image, plus existing text/framing/output reservations. The 2048px dimension cap and default TPM 200000 remain unchanged; a single 2048x2048 image with a short question fits that default, while multiple images or long context may not. This is a deliberately conservative deployment policy, not a universal tokenizer bound; the tile margin exceeds documented OpenAI gpt-4o-mini tile pricing (2833 base / 5667 per tile) and the currently documented mini/nano patch schemes. Other providers/custom accounting still need deployment-specific verification. Reference checked 2026-10-12: [OpenAI images and vision](https://developers.openai.com/api/docs/guides/images-vision).

Before acceptance, the same owned-session transaction rechecks key/hash and then checks the current effective SQL history, including its legacy prefix and completed prior turns, plus current input once and locked attachment bytes. A deterministic budget violation rolls back with 422 before message/evidence/outbox/sequence/admission/pin writes. Same-key replay returns its original receipt before this new-input validation. Worker quota checks remain mandatory: replies of earlier queued turns are not yet known at acceptance and may later make the full context exceed budget. Rate availability is not pre-consumed by the preflight; it remains enforced atomically with the call boundary.

UTF-8 text and supported inline images are supported without paid preprocessing. PDF/office parsing, web search and agent/tool loops remain explicit feature-parity blockers unless implemented with equally bounded, separately gated calls; they are not silently omitted from a request.

## Fault validation

Real MySQL 8 / Redis 7 isolated fixtures and mock HTTP providers; no paid requests. Tests cover same-key barriers across repository instances; payload/tenant checks; atomic rollback; sequential context; duplicate publication; pending reclaim; commit-before-ACK; pre/post-call loss; stale fences; DB outage and Redis flush; quota across workers; shared objects and deletion races; HTTP cancellation/history recovery; migration rerun and compatible rollback. SQLite/unit/race tests are supplementary. Every unexecuted matrix row remains unchecked in the roadmap.
